# Working on Jato

- Keep Cargo in charge of dependency resolution, build scripts, linking, testing, and incremental compilation. Exercise changes through real Cargo projects.
- A result is the files a command wrote and what it printed. It may stand in for a later run of the same command line only when everything the earlier run examined is unchanged. Learn what a command examined by observing it. Never infer it from the command's arguments or from what the compiler reports about itself.
- A hit must reproduce the command's files, diagnostics, and exit status. A command that failed, used the network, could not be observed completely, or changed something it had read is run and not stored.
- Keep cache I/O bounded. Publish complete entries transactionally. Believe a record only when it says itself which command it belongs to. Verify restored bytes unless the filesystem checksums them.
- Results are stored relative to the workspace and the target directory. Output that names the real location of either is only reused there. Exercise another target directory, a copied checkout, a path Cargo must escape, and a target directory inside a package Cargo lists.
- A whole build may depend only on what Cargo and its compilers examined outside what the build itself made, or what a recorded build it rests on made. Exercise an empty target, a target another command already used, a variable only Cargo reads, a build script, and a build that fails.
- Change `EPOCH` in `src/command.rs` when the meaning of a recipe or of a record changes.
- Use an isolated target directory and `JATO_CACHE_DIR` when testing. The test harness sets `JATO_EDIT_WINDOW=0` and `JATO_WHOLE_BUILDS=0` unless a test is about editing spells or whole builds, `JATO_BUSY=0` so that what is recorded does not depend on what else the machine is doing, and `JATO_KEEP_FOR=0` where kept compiler state should be replaced at once.
- Run `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, and `cargo test --locked` before release, the last also with `JATO_NOTES=0` and with `JATO_STORAGE=packed`. Set `JATO_TEST_MOLD` to an upstream mold and `JATO_TEST_NIGHTLY` to the pinned nightly rustc to include their tests. Keep README.md, TODO.md, and the concise work journal current. Commit working milestones.
- rustc's saved state is handed on only with the compiler's own checks intact. Qualify changes to it with `JATO_TEST_NIGHTLY`, where the compiler verifies every result it reuses and says when it turns state down. There a library's unedited module keeps the object file the state came with; the test tells such a file from a compiled one by pausing the compiler, never by how long a compilation happens to take. A program's code is generated again in any other target directory, because rustc ties it to the real paths of what it links. Jato may rely on nothing in that state beyond its header and the option bytes after it, and must leave the state out when they are not as expected. A target directory outside the workspace reaches a library's compilation on a descriptor: everything that starts a compiler with Jato's command line has to hold it.
- Observation changes belong with a test of the program that needed them: a linker that moves its output aside, a compiler that links a finished file into its saved state, a build script that starts a compiler.
- The library that watched programs load (`src/fast/shim.rs`) may make only calls that read from the address the filter lets through, after sending a note of each. Whatever it cannot note it makes in the open, where the kernel reports it. It allocates nothing, takes no lock, names no library it needs, and defines nothing but the C library functions it stands in for: every watched program takes its definitions for its own. The kernel's reports and the notes must produce the same records, so run the tests with `JATO_NOTES=0` as well as without.
- When a build is not recorded, say which program caused it and what it touched. When one is recorded that can only be put back where it was made, because Cargo used what was in the target directory before Jato knew of it, say that too. Step around another cache only where its setup is recognized for certain, and leave the person's settings as they are for anything Jato does not run.
- The C compilers and assemblers that build scripts start are answered through names at the head of `PATH`, for build scripts only. Their results are parts of the build like rustc's. A run whose record cannot be kept, and any command that failed without failing the build, is counted as the build's own doing: what it examined must not be lost. Exercise a compilation that fails as an answer, a tool that cannot be recorded, a compiler fed through a pipe, and a header that changes.
- Where the loader looks for a compiler's libraries is no part of which command it is. The list is kept with the result, and a result is used under another list only where the loader would find the same along both. Exercise a build script's compilation made for a check and wanted by a build, and the reverse.
- Cargo is given its tokens in a pipe with a name, so that it starts compilers without copying itself, and only where nothing says how many compilers to run: the number and the arrangement are the person's. A pipe of tokens is no input of anything that takes one. Exercise `-j`, a `jobs` setting, tokens handed down from outside, and a make that is too old.
- What a program keeps for a person in the home directory it finds by the home directory's name. Exercise a checkout directly in the home directory and one further down.
- A build has more files than a process may have open. Exercise putting one back under a low limit.
- A part may look along a `PATH` of its own. The build records what its own `PATH` finds for each name a part looked up.
- What a command reaches by going up from its workspace is recorded where it was and by the way from the workspace, and both must hold. A search through the directories above is recorded by what it found, and it passes through every directory on its way: a name seen in the workspace and again far above it was not searched for. Exercise a crate beside the checkout that differs, a file included from outside, settings above one checkout, checkouts at different depths, and a directory named like one at the top of the filesystem.
- What Cargo itself reads in a git repository's own directory tells it which files a package has, and is no input of a build. What any other program reads there is. Tell Cargo from what it starts by the program a process is running. The directories a workspace or a target directory is inside are no inputs either. Exercise a worktree, a clone, a worktree of a bare repository, a commit and a change of branch between two builds, a checkout deleted after its build, and a build script that reads the repository.
- Cargo goes by the names in a directory it lists only where it looks for a package's targets (`src/bin`, `examples`, `tests`, `benches`) and where it finds packages: there it reads or looks for the manifest of every directory it sees, which is how such a directory is told. Its other listings, made on the way to a package's files, are no inputs. What any other program lists is. Exercise a file git does not track at the top of a checkout and inside a package, another target directory beside the default one, a copy without a repository, a package added where a pattern finds them, and a program added under `src/bin`.
- Where a build is shown is no part of which build it is, and how wide a terminal is no part of a compilation: the width only lays diagnostics out, and Cargo shows them again later as they were. Whether the compiler coloured them is part of what it printed. A build that is put back is printed for where it is shown now, without colours where there is no terminal. Exercise a build with a warning made on a terminal and put back in a narrower one and on none, and one made without a terminal and put back on one.
- A build may start from a recorded one whose sources differ only in what compilers that Cargo started itself examined. What those compilers wrote is left out, and Cargo runs them again for the lack of it. File times must play no part, and every file left out has to be there again when Cargo is done: otherwise all of it is taken away and the build made from nothing. What anything Cargo did not start as a compiler examined has to be as it was, and so has what Cargo itself read or listed, with one exception below. A build in which a rebuilt build script ran is not recorded. Exercise a change that looks older than the earlier build, a file only a procedural macro reads, a changed input of a build script, a changed build script, changed C that a build script compiles, a build that fails and is mended, and the doubt, which `JATO_TEST_DOUBT` pretends.
- The exception is what only Cargo examined: a manifest or a lock file, the entries of a directory it finds packages or targets in, a file it asked about. Cargo plans the build with them again, and what follows for each compilation is Cargo's to see by what it remembers of it. Its settings are no such thing (`.cargo`, `rust-toolchain.toml`): they reach compilers in ways it does not remember. Nor is what it found in the target directory.
- A build's record says for each build script, a program Cargo started from the target directory, what it and everything it started examined and wrote. A changed input of a build script has that script run again: the compiler that made its program is left out with what the script wrote, and Cargo runs the script because its program was made again. If the program is there afterwards and was not run, the build is made from nothing. What a program examined that is neither Cargo's own nor part of what a build script did leaves nothing to start from, and so does a build script no compiler of the build made.
- Where Cargo planned a build again, a compilation of the earlier build that Cargo did not ask about is no part of it: what it wrote is taken away and is not owed, with what a build script wrote whose program went that way and what Cargo kept for itself in a directory it no longer looked at. Wherever a build script ran again, what it wrote before and not this time is taken away. Nothing the earlier build wrote outside the target directory is put back or removed, and no left-out file outside it is ever removed.
- Qualify such builds two ways, in the suite and on a large workspace's own history: file for file against a build of the same sources from nothing with a cache of its own, and by asking for every compilation one at a time (`JATO_WHOLE_BUILDS=0`, another target directory) and seeing each kept one answered by a record that matches. Exercise a manifest that says more and changes nothing; a changed edition; a new version, with the lock file Cargo then writes and with a build script; a program and a crate that are new; a manifest and a file a build script reads; a header of C a build script compiles; and settings, which leave nothing.
- A process is the one a build script was started in for as long as it runs that program, however many calls the build has reported since. Attribution that lapses makes strays of everything a long build script touches.
- A build whose output names where it was made is put back whole only there. Elsewhere a build starts from it when its record says which of Cargo's compilers wrote every such output: those are left out and run again. Output that names the place and is nobody's to write again leaves nothing to start from. Exercise a program that embeds its checkout's path, built in a second checkout and a third, and put back in each.
- A build made in a target directory that holds another command's recorded build, every input of which is as it was, rests on that build: its record takes in the other's files and conditions and keeps the other's compilers apart from its own. Only its own have to be made again when a build starts from the record. Exercise a build after a check in one target directory put back alone in a new checkout, and a change to a crate both commands compile.
- The command's own program is any that its first process has run after the one that started it. Cargo is one of them where a subcommand it turned into starts it again for the build. Exercise clippy in a worktree and in one with a change.
- Text in the target directory that names a root is known by what it says without the roots' names, to whoever reads it as to whoever wrote it. Exercise generated source that names its checkout.
- A thread that ends while one of its calls waits to be looked at never makes the call. That is no gap in a record. Anything else that keeps a call from being made out is, and the record says which program it was.
- The files of a build that is put back get one time, taken before its sources are looked at and just before anything written from then on, and a file outside the target directory that is already right keeps its own. Exercise an edit made the instant after a restore, one made while the files are being written, and a lock file the recorded build wrote.
- Build, test and measure on a build server where there is one, not on the machine a person is working at, and on a filesystem that clones files as well as on one that does not: the suite passes on both, and what was wrong on ext4 only showed there. `JATO_RECIPES` names a directory to compare two runs by when a command of one was not found for the other.
- Measure on the whole of a large workspace as well as on one package of it, in the person's own environment. Most of what was wrong with whole builds only showed there. Try the commands a person uses one after another in one target directory, check, build, clippy and test, and then in another order in a new worktree: what was wrong between commands only showed that way.
- Use `bench/compare.py` for comparisons with other caches. It gives each contender a private store, daemon, project copy and targets, and runs the built program after every step. Include cold builds, fresh builds and edits alongside restores. On a machine that others build on, run the contenders at the same time, one command each: one after the other, builds from nothing differed by a factor of three either way with what else was running. Compare in a clone of a git repository, not in an exported copy: most of what kept builds from being put back in worktrees only showed there. Record workload, profile, repetitions, machine details, and the load at the time with any performance claim.
- Use `bench/concurrent.py` for builds started together, with and without the limit on running compilers, and `bench/feedback.py` for save-to-diagnostic latency.
- Compare an observed and an unobserved run of the same compilation in alternation when changing the observer. The cost of observation depends on how busy the machine is, which is why compilations in a built target are left unwatched on a busy one. Never take a baseline with `JATO_DISABLE=1` in a target Jato built: build scripts then see other compilers, and Cargo builds everything again.
