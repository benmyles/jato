# Working on Jato

- Keep Cargo in charge of dependency resolution, build scripts, linking, testing, and incremental compilation. Exercise changes through real Cargo projects.
- A result is the files a command wrote and what it printed. It may stand in for a later run of the same command line only when everything the earlier run examined is unchanged. Learn what a command examined by observing it. Never infer it from the command's arguments or from what the compiler reports about itself.
- A hit must reproduce the command's files, diagnostics, and exit status. A command that failed, used the network, could not be observed completely, or changed something it had read is run and not stored.
- Keep cache I/O bounded. Publish complete entries transactionally. Believe a record only when it says itself which command it belongs to. Verify restored bytes unless the filesystem checksums them.
- Results are stored relative to the workspace and the target directory. Output that names the real location of either is only reused there. Exercise another target directory, a copied checkout, a path Cargo must escape, and a target directory inside a package Cargo lists.
- A whole build may depend only on what Cargo and its compilers examined outside what the build itself made. Exercise an empty target, a target another command already used, a variable only Cargo reads, a build script, and a build that fails.
- Change `EPOCH` in `src/command.rs` when the meaning of a recipe or of a record changes.
- Use an isolated target directory and `JATO_CACHE_DIR` when testing. The test harness sets `JATO_EDIT_WINDOW=0` and `JATO_WHOLE_BUILDS=0` unless a test is about editing spells or whole builds, `JATO_BUSY=0` so that what is recorded does not depend on what else the machine is doing, and `JATO_KEEP_FOR=0` where kept compiler state should be replaced at once.
- Run `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, and `cargo test --locked` before release, the last also with `JATO_NOTES=0` and with `JATO_STORAGE=packed`. Set `JATO_TEST_MOLD` to an upstream mold and `JATO_TEST_NIGHTLY` to the pinned nightly rustc to include their tests. Keep README.md, TODO.md, and the concise work journal current. Commit working milestones.
- rustc's saved state is handed on only with the compiler's own checks intact. Qualify changes to it with `JATO_TEST_NIGHTLY`, where the compiler verifies every result it reuses and says when it turns state down. There a library's unedited module keeps the object file the state came with; the test tells such a file from a compiled one by pausing the compiler, never by how long a compilation happens to take. A program's code is generated again in any other target directory, because rustc ties it to the real paths of what it links. Jato may rely on nothing in that state beyond its header and the option bytes after it, and must leave the state out when they are not as expected. A target directory outside the workspace reaches a library's compilation on a descriptor: everything that starts a compiler with Jato's command line has to hold it.
- Observation changes belong with a test of the program that needed them: a linker that moves its output aside, a compiler that links a finished file into its saved state, a build script that starts a compiler.
- The library that watched programs load (`src/fast/shim.rs`) may make only calls that read from the address the filter lets through, after sending a note of each. Whatever it cannot note it makes in the open, where the kernel reports it. It allocates nothing, takes no lock, names no library it needs, and defines nothing but the C library functions it stands in for: every watched program takes its definitions for its own. The kernel's reports and the notes must produce the same records, so run the tests with `JATO_NOTES=0` as well as without.
- When a build is not recorded, say which program caused it and what it touched. Step around another cache only where its setup is recognized for certain, and leave the person's settings as they are for anything Jato does not run.
- The C compilers and assemblers that build scripts start are answered through names at the head of `PATH`, for build scripts only. Their results are parts of the build like rustc's. A run whose record cannot be kept, and any command that failed without failing the build, is counted as the build's own doing: what it examined must not be lost. Exercise a compilation that fails as an answer, a tool that cannot be recorded, a compiler fed through a pipe, and a header that changes.
- A part may look along a `PATH` of its own. The build records what its own `PATH` finds for each name a part looked up.
- What a command reaches by going up from its workspace is recorded where it was and by the way from the workspace, and both must hold. A search through the directories above is recorded by what it found, and it passes through every directory on its way: a name seen in the workspace and again far above it was not searched for. Exercise a crate beside the checkout that differs, a file included from outside, settings above one checkout, checkouts at different depths, and a directory named like one at the top of the filesystem.
- What Cargo itself reads in a git repository's own directory tells it which files a package has, and is no input of a build. What any other program reads there is. Tell Cargo from what it starts by the program a process is running. The directories a workspace or a target directory is inside are no inputs either. Exercise a worktree, a clone, a worktree of a bare repository, a commit and a change of branch between two builds, a checkout deleted after its build, and a build script that reads the repository.
- A build may start from a recorded one whose sources differ only in what compilers that Cargo started itself examined. What those compilers wrote is left out, and Cargo runs them again for the lack of it. File times must play no part, and every file left out has to be there again when Cargo is done: otherwise all of it is taken away and the build made from nothing. What Cargo read or listed, and what anything it did not start as a compiler examined, has to be as it was. A build in which a rebuilt build script ran is not recorded. Exercise a change that looks older than the earlier build, a file only a procedural macro reads, a changed manifest, a changed input of a build script, a changed build script, changed C that a build script compiles, a build that fails and is mended, and the doubt, which `JATO_TEST_DOUBT` pretends.
- A thread that ends while one of its calls waits to be looked at never makes the call. That is no gap in a record. Anything else that keeps a call from being made out is, and the record says which program it was.
- The files of a build that is put back get one time from the filesystem, just before anything written afterwards, and a file outside the target directory that is already right keeps its own. Exercise an edit made the instant after a restore, and a lock file the recorded build wrote.
- Measure on the whole of a large workspace as well as on one package of it, in the person's own environment. Most of what was wrong with whole builds only showed there.
- Use `bench/compare.py` for comparisons with other caches. It gives each contender a private store, daemon, project copy and targets, and runs the built program after every step. Include cold builds, fresh builds and edits alongside restores. Record workload, profile, repetitions, machine details, and the load at the time with any performance claim.
- Use `bench/concurrent.py` for builds started together, with and without the limit on running compilers, and `bench/feedback.py` for save-to-diagnostic latency.
- Compare an observed and an unobserved run of the same compilation in alternation when changing the observer. The cost of observation depends on how busy the machine is, which is why compilations in a built target are left unwatched on a busy one. Never take a baseline with `JATO_DISABLE=1` in a target Jato built: build scripts then see other compilers, and Cargo builds everything again.
